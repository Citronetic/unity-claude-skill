이 튜토리얼에서는 프로파일러를 사용하여 씬을 분석하고 최적화 병목 현상이 발생하는 위치를 식별하는 방법을 알아보겠습니다.

이 튜토리얼에서 배울 내용은 다음과 같습니다.

- 프로파일러 창에서 CPU 프로파일러를 사용하여 CPU 시간을 가장 많이 사용하는 스크립트 메서드를 추론합니다(그렇지 않은 스크립트 메서드와 비교).
- Update() 호출 시 컬렉션을 효율적으로 한 번 통과하는 단일 루프와 동일한 컬렉션을 통과하는 여러 루프 간의 차이점을 구분합니다.
- 주어진 시나리오에서 성능 문제를 야기할 수 있는 잠재적 문제를 파악합니다(예: 리지드바디 컴포넌트나 콜라이더, 그림자가 너무 많은 경우 등).
- Unity의 Stats 창을 사용하여 화면의 폴리곤 수나 텍스처 크기로 인해, 또는 오브젝트가 너무 많아 발생하는 성능 문제를 조사합니다.
- 불필요하게 중첩된 if 문을 식별합니다.

## 1. 개요

Q&A (0)

프로젝트를 마무리하고 퍼블리싱을 준비할 때에는 리팩터링 중이나 후에 코드에 남아 있는 병목 현상을 식별하고 해결하는 것이 중요합니다. Unity의 프로파일링 툴은 프레임 속도의 저하를 유발할 수 있는 문제를 찾아내는 데 매우 적합합니다. 프로파일러는 어떤 스크립트가 호출되고, 메모리가 어떻게 할당되고 있으며, 화면에 비주얼이 어떻게 렌더링되는지 등 애플리케이션에서 발생하는 일들을 프레임 단위로 정확하게 보여 주는 상세 보고서를 생성합니다. 프로젝트의 성능에 영향을 미치는 모든 것을 프로파일러에서 확인할 수 있습니다.

프로젝트의 성능은 주로 프로젝트가 실행되는 컴퓨터에 따라 크게 다르므로 특정 타겟 디바이스에서 프로젝트를 프로파일링하는 것이 중요하며, 데스크톱과 같이 다양한 하드웨어를 지원하는 타겟이라면 다양한 사양의 여러 디바이스에서 프로젝트를 프로파일링해야 합니다. 특정 프로젝트를 새로운 하이엔드 게이밍 PC에서 실행하는 경우에는 프레임 속도가 매우 높은 반면, 온보드 그래픽 카드를 사용하는 구형 노트북에서는 프레임 속도가 현저히 낮아질 수 있습니다.

프로파일러를 처음 접하는 사용자들이 일반적인 최적화 문제를 보다 쉽게 파악할 수 있도록 최적화 수준이 매우 낮은 씬을 제작했습니다. 이 튜토리얼에서 보게 될 수치는 여러분의 컴퓨터에서 표시되는 수치와 정확히 같지는 않을 수도 있다는 점을 염두에 두시기 바랍니다. 하지만 기존 프레임 속도가 어떻든지, 스크립트를 최적화하면 눈에 띄는 결과를 확인할 수 있을 것입니다.

## 2. 씬 살펴보기

Q&A (0)

프로파일러로 검사할 수 있는 성능 문제의 예를 살펴보겠습니다. 앞서 설명한 바와 같이 이 튜토리얼을 위해 제작한 커스텀 씬을 사용할 예정이며, 이 씬은 프로젝트의 전용 최적화 폴더에 있습니다.

**1.**  프로젝트의 **Optimization 폴더**를 찾고 Scenes 폴더에서 Optimization 씬을 엽니다.

**2**. 씬을 처음으로 열면 회색 평면만 보입니다. 계층 구조에서 OptimManager 스크립트가 연결된 Manager 게임 오브젝트도 볼 수 있습니다.

**3**. 플레이 버튼을 누르고 씬을 관찰합니다.

[Image: image]

**4.** 플레이 모드에 들어가면 평면에 지게차 수천 대가 나타나고, 모든 지게차가 일정한 경계 내에서 회전하고 이동합니다. **Stats** 탭을 열고 현재 컴퓨터의 FPS(초당 프레임 수)를 기록해 둡니다.

**5.** 플레이 모드를 종료하고 인스펙터에서 OptimManager 스크립트를 확인합니다. 이 스크립트는 수많은 지게차를 생성하는 역할을 담당합니다. 지게차 프리팹과 인스턴스 수, 경계의 크기에 대한 변수에 주목하세요.

**6.** 계층 구조에서 Manager 오브젝트를 선택한 다음 Optim Manager 컴포넌트에서 인스턴스 수를 200으로 변경합니다. 플레이 모드로 다시 들어가서 FPS가 어떻게 변경되는지 관찰합니다.

[Image: image]

씬의 지게차 수를 줄이면 전체 FPS가 증가합니다. 애플리케이션에서 프레임 속도가 가장 중요한 상황에서는 이처럼 인스턴스 수를 줄이는 것이 실행 가능한 최적화 솔루션일 수 있습니다. 그러나 애플리케이션에 지게차 2,000대와 프레임 속도 60FPS가 모두 필요한 상황이라면 어떨까요?

이러한 요구 사항을 고려하면 병목 현상이 발생하는 위치를 정확하게 파악하는 것이 중요합니다. 첫 번째 예에서 프레임 속도가 낮았던 것은 단지 화면에 메시가 10배 더 많았기 때문일까요? 모든 오브젝트가 움직이고 있었기 때문이었거나, 아니면 다른 이유 때문일까요? 그에 대한 답을 찾으면 무엇을 해결해야 하는지 정확하게 알 수 있습니다.

프로파일링을 수행하면 어떤 작업이 발생하고 있으며 각 작업에 시간이 정확히 얼마나 소요되는지 파악할 수 있고, 그 결과 정보에 입각한 결정으로 프레임 속도를 개선할 수 있습니다.

## 3. 프로파일링 데이터 수집

Q&A (0)

이 씬에서 Unity가 어떤 작업을 처리하는지 좀 더 자세히 살펴보겠습니다.

**1**. OptimManager의 인스턴스 수를 다시 2,000으로 설정합니다.

**2**. **Window > Analysis > Profiler**를 선택하여 프로파일러를 엽니다.

**3**. 프로파일러 창을 프로젝트 창 옆에 고정합니다.

**4**. 아직 씬에 대해 수집된 데이터가 없으므로 프로파일러는 현재 완전히 비어 있습니다. 플레이 모드를 시작하면 프로파일러가 작동하기 시작합니다. 프로파일러의 레코딩 버튼(빨간색 점)이 활성화되어 있는지 확인한 다음 플레이 버튼을 누릅니다.

[Image: image]

**5**. 프로파일러가 색상으로 구분된 성능 데이터 차트를 기록하기 시작합니다.  1~2초 후에 플레이 모드를 종료합니다. 이제 그동안 애플리케이션에서 발생한 모든 일에 대한 정보를 자세하게 확인할 수 있습니다.

[Image: image]

프로파일러 위쪽 절반은 여러 모듈로 나뉘어 있으며, **CPU Usage**부터 시작됩니다. 이 튜토리얼에서는 이 모듈만 사용합니다.

모듈에는 다양한 카테고리의 작업과 해당 작업의 CPU 사용 현황이 담긴 차트가 포함되어 있습니다. 모듈 왼쪽에는 카테고리별 색상 키가 있습니다. 튀어나온 부분은 특정 프레임에서 이러한 카테고리의 작업 중 하나(예: 렌더링)가 작동하는 데 더 많은 시간이 소요되는 시점을 표시합니다.

파란색 배경은 단순한 배경이 아니며 스크립트가 실행 중임을 나타냅니다. 이렇게 아주 개략적으로 살펴보더라도, 씬 자체를 렌더링할 때보다 훨씬 더 많은 처리 능력을 사용하고 있기 때문에 스크립트에 문제가 있을 가능성이 매우 높다는 점을 파악할 수 있습니다. 스크립트는 잠시 후에 검토하겠습니다.

## 4. 밀리초 예산 수립

Q&A (0)

프로파일러의 아래쪽 절반에는 각 프레임에 정확히 어떤 일이 발생하는지를 시각적으로 요약한 정보가 표시됩니다. 프로파일러의 아래쪽 절반에 막대 그래프가 표시되지 않는 경우 Profiler Module 섹션 바로 아래에 있는 드롭다운에서 **Timeline**을 선택합니다.

[Image: image]

CPU Usage 그래프에서 흰색 세로선은 애플리케이션에서 재생된 프레임 한 개를 나타냅니다. CPU Usage 모듈에서 이 선을 왼쪽 클릭하여 드래그하면 사용량의 변화를 프레임 단위로 확인할 수 있습니다. CPU 사용량이 급증하는 지점의 프레임을 선택합니다.

[Image: image]

위 예에서 강조 표시된 부분에 **CPU: 117.26ms**라고 표기된 것을 볼 수 있습니다. 이는 해당 프레임의 모든 작업을 완료하는 데 소요된 총 시간(밀리초)을 나타냅니다.

프로파일링에서 이 밀리초 완료율은 최종 프레임 속도 목표를 달성하기 위한 핵심 요소이므로, 이 부분을 잘 살펴보는 것이 좋습니다. 목표 프레임 속도에 따라 프레임당 특정 밀리초 예산이 책정됩니다. 밀리초 예산을 계산하는 방법은 다음과 같습니다.

**1,000ms / 목표 초당 프레임 수 = 밀리초 예산**

따라서 60FPS라는 목표에 도달하기 위한 각 프레임의 밀리초 예산은 16입니다. 이는 현재 프로파일링 중인 프레임 수가 정상적인 프레임 수보다 7배 이상 많다는 것을 의미합니다.

## 5. 프로파일러 타임라인 살펴보기

Q&A (0)

프로파일러 타임라인 상단에는 번갈아 나타나는 두 개의 레이블(**PlayerLoop**와 **EditorLoop**)이 있습니다. 이 레이블이 표시되지 않는 경우, 스크롤 휠이나 트랙패드를 사용하여 확대해야 합니다. PlayerLoop는 게임 자체에서 실행 중인 모든 작업을 나타내는 반면, EditorLoop는 에디터에서 애플리케이션을 실행할 때 발생하는 모든 작업을 나타냅니다. 최종 사용자는 Unity 에디터에서 앱을 사용하는 것이 아니기 때문에 EditorLoop는 무시하고 PlayerLoop에서 발생하는 작업에만 집중해도 괜찮습니다.

PlayerLoop 아래에 나열된 막대는 해당 프레임이 재생되는 동안 애플리케이션에서 발생하는 모든 작업을 위에서부터 시간 길이가 긴 순서대로 보여 줍니다. 프로파일러 타임라인의 색상은 CPU Usage 그래프와 일치하도록 지정되어 있습니다. 큰 파란색 막대는 이 프레임에서 많은 시간을 소모하는 특정 스크립트 관련 액션이 발생하고 있음을 나타냅니다.

[Image: image]

이 막대를 클릭하면 이 동작의 출처가 OptimUnit 스크립트이며, 그중에서도 Update 메서드임을 알 수 있습니다. 이 동작은 완료하는 데 98.27ms가 걸리며, 이는 여기에 책정된 밀리초 예산을 몇 배나 초과하는 시간입니다. 또한 이 프레임에서 실행 중인 이 스크립트의 인스턴스 수가 2,000개라는 점을 주목하세요. OptimManager 스크립트에서 생성 중인 지게차가 2,000대임을 생각해 보면 이는 중요한 사실입니다. 즉, 이 두 요소가 어떤 식으로든 서로 관련되어 있다는 것입니다.

스크립트가 2,000번 실행되는 이유가 무엇일까요? 지게차 1대마다 인스턴스가 1개이기 때문입니다. OptimManager에서 OptimUnit 프리팹을 선택하면 OptimUnit 스크립트가 프리팹 자체에 연결되어 있다는 사실을 알 수 있으며, 이는 곧 이 스크립트의 사본 2,000개가 실행되고 있음을 의미합니다.

다음으로, 프로파일러를 사용하여 이 프로젝트의 속도를 느려지게 만드는 코드 라인을 정확하게 찾아낼 수 있습니다.

## 6. 프로파일러 샘플 메서드 추가

Q&A (0)

OptimUnit 스크립트의 Update 메서드에서는 많은 작업이 발생하므로 프로파일러의 도움을 좀 더 받도록 하겠습니다. Profiler.BeginSample과 Profiler.EndSample 메서드를 추가하면 코드의 특정 섹션을 프로파일링할 수 있습니다.

**1**. Optimization 폴더에서 Scripts 폴더를 찾아 OptimUnit 스크립트를 엽니다.

Update 메서드는 시간 처리, 지게차 프리팹 회전, 지게차 프리팹 이동, Manager의 경계 확인 등 4가지의 개별 작업을 처리합니다. 프로파일러가 추적할 수 있도록 이러한 작업에 플래그를 지정해 보겠습니다.

**2**. 다음과 같이 Update 상단의 HandleTime 메서드 바로 위와 아래에 BeginSample 메서드와 EndSample 메서드를 추가합니다.

```csharp
Profiler.BeginSample("Handling Time"); // 커스텀 레이블로 코드 프로파일링 시작
HandleTime();
Profiler.EndSample(); // 현재 프로파일링 샘플 종료
```

Profiler.BeginSample에 커스텀 태그 이름을 선언하는 파라미터가 있습니다. 이 레이블은 'OptimUnit.Update'와 동일한 방식으로 프로파일러에 표시됩니다.

**3**. 다음과 같이 Profiler.EndSample 메서드 바로 뒤에 회전을 위한 새 BeginSample을 추가합니다.

```csharp
Profiler.BeginSample("Rotating"); // 프로파일링 시작

var t = transform;
float xRotation = currentAngularVelocity * Time.deltaTime;
float zRotation = currentAngularVelocity * Time.deltaTime;

if (transform.position.x > 0)
    xRotation *= -1;

if (transform.position.z < 0)
    zRotation *= -1;

transform.Rotate(xRotation, 0, zRotation);

Profiler.EndSample(); // 프로파일링 종료
```

**4**. 다음과 같이 지난 EndSample 바로 아래에 새 BeginSample을 추가합니다. 이 메서드는 이동을 위한 것입니다.

```csharp
Profiler.BeginSample("Moving"); // 프로파일링 시작

Move();

Profiler.EndSample(); // 프로파일링 종료
```

**5**. 마지막으로, 이전 EndSample 바로 밑에 BeginSample을 하나 더 추가합니다. 이번에는 경계 확인을 위한 것입니다.


## 7. 코드 최적화

Q&A (0)

**1**. OptimUnit 스크립트로 돌아가 Update에서 Move 메서드가 보일 때가지 아래로 스크롤합니다. Ctrl(Windows) 또는 Cmd(Mac) 키를 누른 상태에서 **Move**를 왼쪽 클릭하여 메서드 자체로 바로 이동합니다.

```csharp
void Move()
{
    Vector3 position = transform.position;

    float distanceToCenter = Vector3.Distance(Vector3.zero, position);
    float speed = 0.5f + distanceToCenter / areaSize.magnitude;

    int steps = Random.Range(1000, 2000);
    float increment = Time.deltaTime / steps;
    for (int i = 0; i < steps; ++i)
    {
        position += currentVelocity * increment * speed;
    }

    transform.position = position;

    transform.position = transform.position + currentVelocity * Time.deltaTime;
}
```

Move 메서드는 몇 가지 변수를 계산하고 for loop를 1,000회에서 2,000회 가량 반복하여 지게차의 새 위치를 계산합니다. 계산한 값에 지게차 대수인 2,000을 곱하고(200~400만 루프가 생성됨) 이 메서드가 프레임당 한 번씩 실행된다는 점을 생각해 보면 이 메서드가 왜 그렇게 느린지 쉽게 이해할 수 있습니다. 이 계산은 Boundary Check 코드에서 계산되는 currentVelocity 계산과 중복되므로, 지게차 이동만 처리하도록 메서드를 단순화할 수 있습니다.

**2**. Move 코드의 본문을 다음 라인으로 대체합니다.

```csharp
void Move()
{
    transform.position = transform.position + currentVelocity * Time.deltaTime;
}
```
