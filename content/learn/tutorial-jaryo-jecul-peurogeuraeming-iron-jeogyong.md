## 2. 개요

Q&A (0)

이전 튜토리얼에서는 객체 지향 프로그래밍의 4가지 핵심 원칙과 그 적용 방법을 알아보았습니다.

- **추상화**: 반복되는 세부 사항이나 정보를 추상화하여 중복 코드를 제거합니다.
- **캡슐화**: 데이터와 데이터를 조작하는 메서드를 클래스에 함께 캡슐화하여 해당 데이터가 다른 클래스에서 오용되지 않도록 보호합니다.
- **상속**: 자식 클래스의 동작이 부모 클래스에서 파생(이를 '상속'이라고 칭함)됩니다.
- **다형성**: 메서드를 여러 가지('다') 형태로 변경('형성')합니다(예: 메서드 오버로드, 메서드 오버라이드).

이번 제출 과제에서는 프로젝트를 처음부터 새로 만들면서 이러한 핵심 원칙을 코드에 적용합니다.

코딩을 시작하기 전에 프로그램의 아키텍처를 개략적으로 구상해 보시기 바랍니다. 이 과정에서 버전 관리 소프트웨어를 사용하여 코드를 브랜치하고 병합하는 방법을 실습해 볼 수 있습니다.

이 과제는 결코 쉽지 않지만 과제를 완료할 무렵에 여러분은 보다 주도면밀하고 전략적인 프로그래머로 성장해 있을 것입니다.

완성된 제출 자료에 포함할 내용은 다음과 같습니다.

- 프로젝트의 GitHub 저장소 링크(커밋 메시지가 포함된 커밋 여러 개와 2개 이상의 브랜치 포함)
- 추상화 시연(불필요한 세부 사항을 추상화하는 더 높은 수준의 메서드)
- 상속 시연(부모/자식 클래스)
- 다형성 시연(메서드 오버라이드 또는 오버로드)
- 캡슐화 시연(게터와 세터)

## 4. 프로젝트 설계

Q&A (0)

프로젝트와 저장소가 생성되었으므로, 이제 시간을 할애하여 객체 지향 프로그래밍의 4가지 핵심 원칙을 시연할 수 있는 프로젝트 컨셉을 생각해 보세요.

이 프로젝트는 완성된 형태의 실제 프로젝트라기보다는 프로토타입에 가깝습니다. 기본적인 형태를 사용하거나 완전히 텍스트에 기반한 프로젝트여도 괜찮습니다. 그렇다고 백지 상태에서 시작해야 할 필요는 없습니다. 코드로 창작하기를 완료했다면 프로토타입이나 과제 중 하나의 에셋을 재사용해도 됩니다. 이 과제의 목표는 시각적인 걸작을 처음부터 새로 만들어 내는 것이 아니라, OOP(객체 지향 프로그래밍)의 핵심 원칙인 추상화, 캡슐화, 상속, 다형성을 시연하는 창의적 프로젝트를 기획하는 것입니다.

[Image: image]

컨셉을 발전시키면서 떠오르는 아이디어를 **설계 문서** 또는 **프로젝트 브리프**에 정리하고 되돌아보세요. 코드로 창작하기를 완료했다면 [개인 프로젝트 실습](https://learn.unity.com/tutorial/lab-1-personal-project-plan?uv=2020.3&courseId=5cf96c41edbc2a2ca6e8810f&projectId=5caccdfbedbc2a3cef0efe63)에서 사용했던 템플릿에서 아이디어를 얻는 것도 좋습니다. 얼마 전 진행했던 리소스 관리 프로젝트의 [설계 브리프](https://connect-prd-cdn.unity.com/20210602/7105725f-6cb4-4171-a399-ba1b485a7e96/Project_Brief.pdf?_gl=1*wjdq4t*_ga*NDI3MDM1NDEuMTU5MjI0OTM3NA)를 활용할 수도 있습니다. 문서는 글머리 기호를 붙인 개요, 스케치, 다이어그램을 비롯하여 아이디어를 효율적으로 정리하고 반복하는 내용이라면 무엇이든 포함할 수 있습니다.

물론 일반적인 프로젝트 개발 과정에서는 프로그래밍 컨셉을 시연한다는 목적으로 프로젝트의 성격이 정해지지는 않습니다. 사실은 그 반대입니다. 프로젝트의 성격이 프로그래밍 컨셉에 대한 요구 사항을 결정하는 것입니다. 하지만 이러한 우선순위를 뒤집어 봄으로써 설계 과제를 더 즐겁게 진행할 수 있습니다. 어떻게 하면 이러한 4가지 프로그래밍 컨셉을 모두 사용하는 프로젝트를 설계할 수 있을까요? 다음 순서에 따라 핵심 원칙을 고찰해 보는 것이 가장 좋습니다.

**1.  상속 - 오브젝트 선택**

브레인스토밍을 시작해 보겠습니다. 보다 일반적인 오브젝트의 동작을 가져와 사용하는 오브젝트에는 어떤 것들이 있을까요? 다른 오브젝트의 하위 유형이라고 생각되는 오브젝트는 무엇인가요? 예를 들면 다음과 같습니다.

- 동물 → 고양이 / 개
- 운송 수단 → 비행기 / 자동차 / 배
- 토스터 → 기본 토스터 / 디럭스 토스터 / 프리미엄 토스터

위 예시는 코드에서 상속을 통해 구현할 수 있는 부모/자식 관계를 보여 주는 몇 가지 사례입니다. 이 원칙에 대한 자세한 내용은 [상속 튜토리얼](https://learn.unity.com/tutorial/inheritance-and-polymorphism-in-object-oriented-programming)을 참조하세요.

**설계 문서 또는 프로젝트 브리프**에서 수행할 작업:

프로젝트 컨셉의 시작점으로 삼고자 하는 오브젝트를 적어 둡니다.

**2.  다형성 - 동작 선택**

프로젝트에 사용할 오브젝트의 유형과 하위 유형을 결정한 후에는, 프로그램에서 해당 오브젝트가 수행하는 동작의 유형을 생각하고 해당 동작이 오브젝트 하위 유형에 따라 어떻게 변형될 수 있을지 고민해 봅니다. 예를 들면 다음과 같습니다.

- 모든 동물에게 Jump() 함수를 부여할 수 있지만 고양이와 개의 점프 능력은 다를 것입니다.
- 모든 운송 수단에 Move() 함수를 부여할 수 있습니다. 이때 비행기는 3차원의 모든 방향으로 이동할 수 있지만 뒤로 이동할 수는 없습니다.
- 모든 토스터에 Toast() 함수를 부여할 수 있지만 프리미엄 토스터에는 특별한 '베이글' 설정이 포함될 수 있습니다.

이미 알고 계시겠지만 다형성은 같은 이름의 메서드가 다양한 파라미터를 통해 오버로드되어 여러 형태('다' + '형성')를 가질 수 있다는 사실을 뜻하기도 합니다. 또한 이러한 메서드가 취할 수 있는 다양한 파라미터 입력을 생각해 볼 수도 있습니다. 예를 들어, Jump() 함수에는 최대 점프 높이 [Jump(float maxHeight)] 또는 여기에 적용되는 힘 [Jump(Vector3 jumpForce)]가 포함될 수 있습니다.

이 핵심 원칙에 대한 자세한 내용은 [다형성 튜토리얼](https://learn.unity.com/tutorial/inheritance-and-polymorphism-in-object-oriented-programming)을 참조하세요.

**설계 문서 또는 프로젝트 브리프**에서 수행할 작업:

애플리케이션에 프로그래밍하려는 기능 또는 동작의 유형을 적어 둡니다.

**3.  캡슐화 - 데이터 선택**

캡슐화의 주된 목적은 클래스의 데이터를 보호하여 해당 데이터가 오용되거나 애플리케이션이 손상되지 않도록 하는 것입니다. 이 방식으로 어떤 데이터를 보호할지와, 보호한 데이터를 가져오거나 설정할 수 있도록 유지할 일부 클래스에 대해 생각해 보세요. 예를 들면 다음과 같습니다.

- 동물의 경우 이름을 가져오거나 설정해야 할 수 있습니다. 이때 이름이 너무 길어지지 않도록 합니다.
- 운송 수단의 경우 연도를 가져오거나 설정해야 할 수 있습니다. 이때 연도는 음수가 아니어야 합니다.
- 토스터의 경우 빵의 유형을 가져오거나 설정해야 할 수 있습니다. 이때 빵 옵션이 유효한지 확인합니다.

이 핵심 원칙에 대한 자세한 내용은 [캡슐화 튜토리얼](https://learn.unity.com/tutorial/encapsulation-in-object-oriented-programming)을 참조하세요.

**설계 문서 또는 프로젝트 브리프**에서 수행할 작업:

프로젝트에 캡슐화하려는 기능 또는 데이터의 유형을 기록해 둡니다.

**4.  추상화 - 함수 선택**

이미 코딩 작업을 진행 중이라면 구현하기 가장 쉬운 컨셉은 바로 추상화입니다. 하지만 시작 전에 프로젝트에 구현하려는 고수준 함수에 대해 미리 생각해 보면 큰 도움이 됩니다. 예를 들면 다음과 같습니다.

- 동물의 경우 Walk(), Jump(), Talk() 등의 함수를 사용할 수 있습니다.
- 운송 수단의 경우 TurnOn(), Move(), TurnOff() 등의 함수를 사용할 수 있습니다.
- 토스터의 경우 Start(), SetLevel(), Cancel() 등의 함수를 사용할 수 있습니다.

이 핵심 원칙에 대한 자세한 내용은 [추상화 튜토리얼](https://learn.unity.com/tutorial/abstraction-in-object-oriented-programming)을 참조하세요.

**설계 문서 또는 프로젝트 브리프**에서 수행할 작업:

코드에서 유용하게 재사용할 수 있을 만한 고수준 함수를 적어 둡니다.

아직은 개념적인 느낌이 강하지만, 이제 프로젝트에서 구현하려는 아이디어가 있고 그러한 아이디어를 문서에 기록해 두었습니다.

어떤 내용의 프로젝트를 만들지 여전히 막연하게 느껴진다면 다음 아이디어를 참조해 아주 간단한 프로젝트를 설계해 보세요.

- 기본 'shape' 클래스에서 상속되는 세 가지 색상의 셰이프가 있습니다(상속).
- 각 셰이프를 클릭하면 오버라이드된 DisplayText() 함수를 통해 화면에 다소 다른 형태의 셰이프가 출력됩니다(다형성).
- 각 셰이프에는 이름이나 색상과 같은 데이터가 포함되어 있으며, 해당 데이터는 게터와 세터를 통해 프로퍼티로 저장됩니다(캡슐화).
- 코드는 더 높은 수준의 메서드를 통해 중복 코드를 최소화하는 방식으로 구성됩니다(추상화).

## 5. 타이틀 화면을 위한 브랜치 생성 및 변경 사항 커밋

Q&A (0)

여러 개발자와 작업을 수행하는 경우에는 **브랜치**가 특히 버전 관리에 유용합니다. 일반적으로 개발자는 새 기능을 구현하기 시작할 때 새 브랜치를 시작하고, 다른 개발자가 실험하는 코드에는 그 실험이 끝날 때까지 관여하지 않으려 합니다.

새 기능을 구현한 후에는 브랜치를 메인 브랜치에 **병합**한 다음 병합으로 인해 발생하는 **병합 충돌** 문제를 처리합니다. 병합 충돌에 대해 잘 기억나지 않는다면 [버전 관리 설정](https://learn.unity.com/tutorial/set-up-version-control) 튜토리얼을 다시 살펴보세요.

이 프로세스에 익숙해질 수 있도록 프로젝트의 타이틀 화면에 활용할 새 브랜치를 생성하고 병합해 보겠습니다. 앱에서 타이틀 화면이 호출되지 않는 경우 이 기능 대신 프로젝트의 다른 간단한 기능을 사용하세요.

**1.**저장소에 새 브랜치를 생성하고 'title-screen'과 같은 이름을 지정합니다. 새 브랜치를 생성하는 방법을 잘 모르는 경우 [GitHub 기술 자료의 지침](https://docs.github.com/en/desktop/contributing-and-collaborating-using-github-desktop/making-changes-in-a-branch/managing-branches#creating-a-branch)을 따르세요. 이 브랜치에서는 다른 개발자의 작업을 방해하지 않으면서 새 기능을 안전하게 실험할 수 있습니다.

[Image: image]

이제 'Current branch'가 새 브랜치로 설정되어 있는 것을 확인할 수 있습니다.

[Image: image]

**2.**새 브랜치에서 타이틀 화면을 개발합니다. 프로젝트에서 제출할 결과물에 사용할 간단한 타이틀 화면을 만듭니다. 아래 예시처럼 이 화면은 여러분이 정한 프로젝트 컨셉과 연관되어 있으면서도 단순해야 합니다.

[Image: image]

작업을 진행하고 저장하는 동안 브랜치에서 편집하거나 추가한 모든 사항이 버전 관리 소프트웨어의 **Changes** 패널에 반영됩니다.

**3.**이 브랜치의 변경 사항을 메인 브랜치와 병합하려면 해당 변경 사항을 **커밋**합니다. 버전 관리 소프트웨어에서 요약과 설명을 추가한 다음 **commit to [브랜치-이름]**을 선택합니다.

[Image: image]

이제 변경 사항이 브랜치에 커밋되었고 마스터 브랜치와 병합될 준비가 되었습니다.

## 6. 브랜치를 마스터 브랜치와 병합

Q&A (0)

타이틀 화면(또는 다른 기능)이 완성되었으므로 이제 실험 브랜치를 메인 개발 브랜치에 병합할 수 있습니다.

**1.**마스터 브랜치로 돌아가려면 **Current Branch** 드롭다운을 사용하여 **main** 브랜치를 선택합니다.

[Image: image]

메인 브랜치로 다시 전환하면 모든 변경 사항이 Unity 씬에서 사라진 것을 볼 수 있습니다. 이는 새 기능 구현을 시작하기 전의 프로젝트 상태로 돌아왔기 때문에 발생하는 현상으로 자연스러운 상황이며 걱정할 필요가 없습니다. 해당 기능은 대규모 병합 후 프로젝트에 다시 나타납니다.

마지막 커밋 이후 내용을 변경한 경우 변경 사항을 브랜치에 남겨둘 것인지, 아니면 메인 브랜치로 가져올 것인지를 선택하라는 메시지가 표시됩니다. 이는 브랜치에 아직 커밋하지 않은 변경 사항이 있음을 뜻합니다. Cancel 버튼을 누르고 모든 변경 사항이 브랜치에 커밋되었는지 확인한 후 다시 메인 브랜치로 전환을 시도해 보세요.

[Image: image]

**2.**브랜치 드롭다운에서 **Choose a branch to merge into main**을 선택합니다. 그런 다음 **Merge [브랜치-이름] into main**을 선택합니다.

[Image: image][Image: image]

Unity 씬으로 돌아오면 브랜치에서 변경한 내용이 이제 메인 브랜치에 반영되어 있습니다. 병합이 무사히 완료된 것입니다.

## 8. 프로젝트 제출

Q&A (0)

프로젝트에 객체 지향 프로그래밍의 핵심 원칙 4가지를 전부 구현했다면 이제 프로젝트를 제출하고 공유할 시간입니다. 그 전에, 철저히 플레이 테스트를 진행했는지 확인해야 합니다. 친구나 가족에게 플레이 테스트를 부탁하면 더 좋습니다.

완성된 제출 자료에 포함할 내용은 다음과 같습니다.

- 프로젝트의 GitHub 저장소 링크(커밋 메시지가 포함된 커밋 여러 개와 2개 이상의 브랜치 포함).
- 상속 시연(부모/자식 클래스). 코드에 상속이 구현된 위치임을 나타내는 '// 상속'이라는 주석을 추가합니다.
- 다형성 시연(메서드 오버라이드 또는 오버로드). 코드에 다형성이 구현된 위치임을 나타내는 '// 다형성'이라는 주석을 추가합니다.
- 캡슐화 시연(게터와 세터). 코드에 캡슐화가 구현된 위치임을 나타내는 '// 캡슐화'라는 주석을 추가합니다.
- 추상화 시연(불필요한 세부 사항을 추상화하는 더 높은 수준의 메서드). 코드에 추상화가 구현된 위치임을 나타내는 '// 추상화'라는 주석을 추가합니다.

프로젝트의 진행 과정에 대한 안내를 받을 수 있도록 프로젝트 스크린샷을 찍거나 화면을 녹화한 다음 여기에 올려 결과물을 공유해 주세요.

한 명 이상의 다른 크리에이터 제출 자료에 댓글을 달 것을 적극 권장합니다. 다른 크리에이터들이 과제를 성공적으로 완료했나요? 해당 프로젝트의 어떤 점이 마음에 들며, 추가하면 좋을 새로운 기능에는 어떤 것이 있을까요?
