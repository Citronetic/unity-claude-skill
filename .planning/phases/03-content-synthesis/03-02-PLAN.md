**Part A: Build synthesize-topic.mjs**

Create `scripts/synthesize-topic.mjs` that takes a topic name as argument and produces an intermediate synthesis file. For each topic it:

1. Reads `synthesis/topic-map.json` to get the list of pages assigned to this topic
2. Prioritizes pages by source quality: manual > learn > api (manual pages are most reference-like)
3. Within each source, sorts by wordCount descending
4. Reads the TOP pages per topic (budget: up to ~50 pages or 100K words, whichever comes first — this keeps context manageable)
5. For each page read, extracts:
   - Code blocks (preserving language annotations)
   - API names mentioned (classes, methods)
   - Key patterns, workflows, and configuration described
   - Any warnings, notes, or version-specific info
6. Outputs a structured synthesis markdown file

The output synthesis file format for each topic:
```markdown
# {Topic Name} — Synthesis Notes

> Source: {N} pages from manual ({M}), learn ({L}), api ({A})
> Generated: {timestamp}
> Status: DRAFT — needs manual curation

## Key Concepts
[Extracted key concepts, 2-3 sentences each, opinionated tone]

## Patterns & Workflows
[Step-by-step patterns rewritten as concise reference, not tutorial]

## Code Examples
[Full code examples with using statements, class context, comments]
[Each example: what it demonstrates, when to use it]

## API Quick Reference
[Key APIs for this topic with one-line descriptions]
[Only the most-used APIs, not exhaustive list]

## DO / DON'T
[Deprecated patterns from deprecated-patterns.md for this topic]
[Additional anti-patterns found in source content]

## Version Notes
[Unity 6.x specific changes relevant to this topic]
```

The script should:
- Accept `--topic=physics` or `--all` to run all topics
- Skip non-English pages (detect by filename patterns)
- Apply the "Claude already knows this" filter: skip sections that are purely generic C# (classes, interfaces, basic OOP), skip content explaining what a variable is, what a loop is, etc.
- For code blocks: ensure `using` statements are present. If a code block references Unity types but lacks `using UnityEngine;` etc., add them.
- For each topic, also read the relevant rows from `synthesis/deprecated-patterns.md` and embed them in the DO/DON'T section.

Run the script with `--all` to generate all 16 files.

**Part B: Manual curation pass**

After the script generates drafts, do a manual curation pass on each file:
- Remove redundant content (same concept explained multiple ways from different source pages)
- Tighten prose to opinionated reference tone ("Use X, not Y. Here's why.")
- Ensure code examples are complete scripts, not fragments
- Remove any tutorial-style progressive building ("First, create a new script... Now, add this line...")
- Add cross-references between related topics where valuable (e.g., physics.md referencing input-system.md for physics-based movement with input)
- Each synthesis file should be self-contained and useful on its own
- Target: 200-500 lines per synthesis file (these are intermediate; final reference files in Phases 5-8 will be under 300 lines)

**Content tone guidelines** (from CONTEXT.md locked decisions):
- Prescriptive: "Use X, not Y. Here's why."
- Direct: No hedging, no "you might want to consider"
- Complete: Full code examples with using statements, class inheritance, comments
- Filtered: Only Unity-specific knowledge. Skip C# basics, OOP concepts, generic programming.
- Opinionated: Recommend one way. Mention alternatives only to steer away from them.

**Filtering heuristic** (SYNTH-05): For each piece of content, ask: "Would Claude produce this guidance correctly from training data alone, without this skill?" If yes, skip it. Focus on:
- Unity-specific API usage patterns and gotchas
- Version-specific behavior (Unity 6.x changes)
- Unity Editor workflows that are not obvious from documentation
- Performance pitfalls specific to Unity's architecture
- Configuration details (inspector settings, project settings)
- Platform-specific considerations
